# Retell AI

Research checked: 2026-09-11. Official documentation research; no live calls, simulations, or paid analysis jobs executed.

## Product vision and users

Retell combines voice-agent operation with testing and call analysis. For this research, distinguish three features: text-based simulation testing, post-call extraction, and AI QA. They serve different purposes and should not be collapsed into one “call success” field. [Simulation testing](https://docs.retellai.com/test/llm-simulation-testing), [Analysis consumption](https://docs.retellai.com/features/post-call-analysis-consumption), [AI QA overview](https://docs.retellai.com/ai-qa/overview)

The relevant users are engineers testing agent changes and operators investigating call quality.

## Core abstraction and data model

| Object | Meaning |
| --- | --- |
| Agent/version | Target configuration used for a call |
| Call | Execution with identity, status, timing, transcript, and optional artifacts |
| Test case | Simulated caller instructions, success criteria, variables, and mocks |
| Test run/batch | Repeated execution of saved test scenarios |
| Call analysis | Extracted fields attached after analysis completes |
| QA cohort | Filtered/sample-selected calls evaluated against criteria |

The Get Call API exposes fields including `call_id`, `agent_id`, `agent_version`, transcript forms, recording references, latency data, and `call_analysis`. These fields may depend on call status and recording/storage configuration; a sample response is not a guarantee that every field is populated. [Get Call reference](https://docs.retellai.com/api-references/get-call)

## Simulation workflow

Define an AI caller, success criteria, variables, and function mocks, then run and review a test or batch. The reviewed documentation says simulation runs as text without placing a call. It supports single-prompt, multi-prompt, and Conversation Flow agents, but not custom-LLM agents. [Simulation testing](https://docs.retellai.com/test/llm-simulation-testing)

Simulation criteria are judged together to produce one run verdict and explanation. A run can also end in an execution error before a verdict. This differs from AI QA's per-metric diagnosis. The docs also describe limits to mocking: unmocked external functions can execute for real, and MCP tools ignore mocks. [Simulation testing](https://docs.retellai.com/test/llm-simulation-testing)

Our interpretation: an evaluation runner needs separate statuses for execution failure and judged behavioral failure, and a precise contract for which tools are simulated.

## Post-call extraction workflow

After a call, extraction results become available in the dashboard, through the Get Call API, or through the **`call_analyzed`** webhook. The documented **`call_ended`** webhook excludes `call_analysis`. Calls without a connected conversation can lack custom extracted fields. [Analysis consumption](https://docs.retellai.com/features/post-call-analysis-consumption)

For our adapter, call completion and analysis completion should be separate events. Missing data means pending or unavailable, not automatically false.

## AI QA and evaluation methods

AI QA groups calls into cohorts, samples them, and applies configured criteria and metrics. Its UI provides trends and call-level evidence concerning resolution, latency, hallucinations, overlapping speech, sentiment, and tool behavior. [AI QA overview](https://docs.retellai.com/ai-qa/overview)

Retell's metric definitions include word error rate, transcription of important entities, naturalness, and hallucination rate. Its WER reference is generated by another transcription process that uses audio and the original transcript; the docs acknowledge that this reference can still contain errors. This is not the same as independently human-transcribed ground truth. [AI QA metric definitions](https://docs.retellai.com/ai-qa/terminologies)

Our interpretation: record how a reference was produced. A mathematically correct WER calculation against an imperfect reference can still misrepresent transcription quality. Do not infer exact recognition accuracy from an unvalidated reference.

## Architecture, SDKs, and integration

The integration flow we would build is:

```text
Retell call -> call record/artifacts
           -> call_analyzed event -> adapter -> our normalized evidence
                                                -> our evaluator results
```

The API reference includes Python and JavaScript SDK examples and the REST retrieval endpoint `GET /v2/get-call/{call_id}`. Transcript objects can carry word timestamps, and recording references include a multichannel form. These are useful inputs for an external evaluator. [Get Call reference](https://docs.retellai.com/api-references/get-call)

The diagram describes a proposed adapter, not Retell's internal architecture. No private database or job-queue implementation was verified.

## Strengths, limitations, and cost

Our assessment:

- Detailed call artifacts make diagnosis more concrete than a summary alone.
- Simulation and production QA offer different kinds of coverage.
- Text simulation does not establish speech or telephone-path quality.
- Model-generated extraction and QA labels require checks against independent evidence.

As checked, the AI QA overview lists **100 free analyzed minutes per workspace**, then **$0.10 per analyzed minute**. This is AI QA pricing, not the full cost of calls or simulation; other charges were not audited. [AI QA overview](https://docs.retellai.com/ai-qa/overview)

## Lessons and hand-coding exercise

Implement an idempotent call-ingestion adapter that accepts separate completion and analysis events. Preserve raw provider data and normalize timestamps/units explicitly. Keep provider-generated scores separate from scores computed by your own evaluators.

Acceptance example: deliver analysis before the completion event, then deliver both again. The database must contain one call with complete evidence and no duplicate score records. A call without audio must remain visibly unscored for audio metrics. This teaches event ordering, deduplication, state transitions, and data normalization.
